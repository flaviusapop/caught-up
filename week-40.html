Your Agents Are in Solitary Confinement: Why MCP & A2A Aren't Enough 

Vlad Luzin, Band

AI & Agents · Engineering & Infrastructure

Vlad Luzin argues that connecting agents requires a collaboration infrastructure layer, not just tool calls or task handoffs. He explains the distributed-systems requirements behind that argument, then demonstrates Band and its Gem desktop application for coordinating local and remote agents alongside humans.

Key points and full summary
  • Developers copying information between coding sessions already perform multi-agent coordination manually; Luzin describes the human as a router between otherwise isolated, stateful agents.
  • Luzin argues that MCP tool calls and A2A task exchange leave substantial application infrastructure unresolved, including durable messaging, session continuity, discovery, and cross-framework state mapping.
  • Remote multi-agent systems combine ordinary distributed-systems problems with nondeterministic participants, requiring retries, ordered delivery, recovery, and deterministic message routing.
  • Band raises the communication abstraction to rooms, channels, and participants, with agent registration, cross-user connection requests, permissions, and bilateral consent.
  • Gem exposes agent-generated tasks, architecture-level activity, human intervention, and token-cost attribution rather than requiring managers to reconstruct progress from long conversations.
  • The demonstration presents messaging as a way for agents to organize review and implementation work without hand-coding every interaction loop; its reliability is asserted rather than systematically evaluated.

Luzin’s central thesis is that autonomous agents will communicate within businesses, across organizations, and between consumers and companies, despite using different frameworks and deployment environments. He grounds this prediction in an existing developer habit: running one coding session to implement changes and another to review them, while manually transferring context between the two. In his framing, the coordination problem already exists; the question is whether developers should continue acting as message routers or build infrastructure that lets agents communicate directly.

He argues that existing protocols and messaging integrations do not by themselves provide that infrastructure. His critique characterizes MCP agent-as-tool calls as stateless and A2A as client-server task exchange, leaving developers to manage reciprocal communication, timeouts, persistent queues, and discovery. Connecting an agent to Slack or Telegram also does not automatically connect it to other agents. Underneath these interfaces are distributed processes that can crash and lose continuity. Luzin therefore calls for ordered delivery, retries, state hydration, and mappings between framework-specific thread, conversation, and execution identifiers. Above transport, he proposes conversation-level abstractions—rooms, channels, and participants—with deterministic routing, identity, and audit controls.

Band is presented as an implementation of this collaboration layer. In the demonstration, Codex and LangGraph agents register programmatically and become visible in the platform. A connection to another user’s personal assistant requires bilateral consent before that assistant can be invited into a conversation. Gem, a desktop application built on Band, adds task tracking, architecture visualization, and cost attribution across local and remote sessions. Luzin shows agents collaborating on requirements and implementation through messages, arguing that models already understand these interaction patterns. The practical promise is less manual routing and better visibility into work, expenditure, and human participation. However, the talk is a vendor demonstration: it does not establish comparative reliability, security guarantees, or whether conversational coordination remains efficient as agent activity grows.

Suggested actions, from the summary
  • Identify where people currently copy context between agent sessions, and separate that coordination work from the agents’ actual implementation tasks.
  • Before connecting remote agents, specify message ordering, retry behavior, persistence, restart recovery, and mappings between framework session identifiers.
  • Define agent discovery, permissions, consent, and audit requirements before enabling cross-user or cross-company collaboration.
  • Track tasks, human interventions, and costs alongside conversations so progress does not depend on reading every token.
Limits of this summary
  • The supplied publisher transcript is untimed; its metadata reports structural validation but does not prove semantic completeness.
  • Protocol limitations and product capabilities are presented from Band’s perspective without independent testing or detailed protocol-version qualifications.
  • The transcript describes visual demonstrations but supplies no implementation artifacts, performance measurements, or security evaluation.

The Death of the Code Review: What the Data Actually Says 

Laurie Voss, Arize AI

Engineering & Infrastructure · Data & Evals · Policy & Safety

Laurie Voss examines whether automated code generation can be matched by automated review, arguing that passing tests is not equivalent to producing mergeable software. His proposed shift is from line-by-line human inspection toward human-designed review harnesses, explicit quality standards, and production evidence—with human accountability retained where automation is weakest.

Key points and full summary
  • Voss cites a study reporting 741% more code but only 30% more shipped software after autonomous-agent adoption, using the mismatch to frame review as a throughput bottleneck.
  • Human review capacity cannot simply expand with generated code volume; he cites historical Cisco findings that defect detection deteriorates with large review batches and high reading rates.
  • Tests and coding benchmarks capture only part of mergeability: maintainability, scope discipline, regression safety, external dependencies, and organizational context also matter.
  • Production reviewers use multiple passes, repository context, tools, and developer acceptance feedback to improve findings and suppress false positives.
  • Experiments without per-change human approval still depend on human-designed test harnesses, feedback systems, and review infrastructure.
  • Automated reviewers are themselves security-sensitive systems; prompt injection and misleading framing can undermine their judgments.
  • Voss recommends investing human effort in review standards, rules, evaluations, and runtime observation rather than treating every pull request as an isolated reading assignment.

Voss opens with a mismatch between the speed of code generation and the speed of trustworthy delivery. He cites research reporting that developers adopting autonomous agents produced 741% more code while shipping only 30% more software. Historical Cisco review research supplies his explanation for why simply assigning more human review is unlikely to close the gap: reviewers lose effectiveness when reading too much code in one sitting or moving too quickly. Large agent-generated pull requests can therefore consume days of serious inspection, while a developer can generate several more in parallel. His question is not whether review matters, but how to make the trust-building process scale.

The key distinction is between passing tests and being genuinely mergeable. Voss describes METR maintainers rejecting roughly half of changes that had passed SWE-bench grading, citing code quality and effects outside the tested behavior. He also discusses a maintainer-oriented benchmark covering regression safety, scope, tests, and maintainability, where reported model performance is much weaker than on conventional coding benchmarks. His broader argument is that cheap verifiers shape model training: once a quality criterion becomes reliably measurable, it can become a training signal. Defining mergeability therefore influences both today’s review harnesses and potentially future model behavior.

Current commercial reviewers illustrate partial progress rather than a solved problem. Voss describes Cursor using repeated review passes to reduce false positives, then moving toward tool-using investigation and agents that propose fixes. Other systems add repository graphs or learn from accepted and rejected suggestions. These workflows still rely on human judgments to define useful findings. Likewise, highly automated compiler-building, code-porting, and internal-product experiments do not eliminate review; they relocate it into tests, execution environments, observability, and agent-review loops. His discussion of Bun’s Rust migration highlights the danger of equating interface-level test success with assurance about memory safety inside numerous unsafe blocks.

The remaining human role is most important where correctness is expensive to verify, failures have a large blast radius, or someone must accept responsibility. Voss also warns that a reviewer can be manipulated by the material it reviews, citing prompt-injection caveats and research on misleading commit framing. Consequently, review harnesses need their own scrutiny, and runtime behavior becomes an essential final source of evidence. His closing instruction to stop reviewing pull requests is best read alongside these qualifications: move scarce human judgment upward into explicit standards, company context, reviewer evaluations, and production monitoring rather than abandoning accountability. The outcome to optimize is defensible trust in shipped software, not generated code volume.

Suggested actions, from the summary
  • Codify mergeability beyond test success, including maintainability, scope boundaries, regression safety, and dependencies outside the repository’s test suite.
  • Evaluate automated reviewers on actionable findings and false positives using accepted and rejected suggestions, not just the number of comments generated.
  • Build a review harness with relevant repository context, execution tools, tests, and explicit company rules; assign humans to evaluate that harness.
  • Retain human checkpoints for high-blast-radius changes and test reviewer defenses against instructions or misleading framing embedded in review inputs.
  • Use production traces and observed behavior to check whether automatically reviewed changes actually deliver their intended outcomes.
Limits of this summary
  • The supplied publisher transcript is untimed and contains redactions and transcription irregularities; semantic completeness is not independently established.
  • The cited studies, benchmark scores, vendor adoption figures, and migration results are speaker-reported and cannot be independently checked from the supplied material.
  • The transcript inconsistently names the maintainer-oriented benchmark and gives an arithmetic gap inconsistent with its stated scores; the summary preserves the qualitative comparison rather than that gap.
  • duration_seconds uses the watch and publisher value of 1480; the supplied videos-tab value is 1481 seconds.
  • The closing recommendation is qualified by the talk’s repeated defense of human oversight for review systems and high-risk changes; it is not evidence that all human review can safely be removed.

The Chief AI Officer: Scientist, Architect, Coach 

Rania Khalaf, WSO2

Leadership & Culture · Startup Strategy · AI & Agents

Rania Khalaf explains the Chief AI Officer role through three adjustable responsibilities: scientist, architect, and coach. Drawing on research leadership, agricultural biotechnology, and WSO2, she shows how company context should determine the mandate, organizational structure, and measures of success.

Key points and full summary
  • The Chief AI Officer mandate varies with company type, AI maturity, and the individual’s strengths; it is not a standardized executive job description.
  • The scientist explores and experiments, the architect shapes strategy and investment, and the coach develops employee and customer understanding.
  • A non-software business may need data integration and practical process improvements more urgently than novel models; Khalaf’s corn-embryo example required simple blob detection rather than machine learning.
  • Khalaf describes her WSO2 allocation as roughly 20% scientist, 60% architect, and 20% coach, with more outward coaching because its workforce is already highly technical.
  • She rejects token consumption as a success metric and instead tracks workforce fluency, distributed builders, workflow adoption, tool access, product readiness, customer adoption, and commercial signals.
  • Agent-ready products require usable interfaces and documentation, appropriate identity and governance, and pricing that accounts for agent-driven consumption.
  • Strong CEO backing, collaboration across functions, and alignment between the role and the leader’s capabilities are prerequisites for a sustainable mandate.

Khalaf presents the Chief AI Officer as an evolving role whose responsibilities depend on the company’s business, AI maturity, and available leadership talent. Her organizing framework has three dimensions. The scientist keeps experimenting with rapidly changing technology and may also lead original research. The architect turns possibilities into product strategy, operating changes, investment decisions, and board-level accountability. The coach educates employees and advises customers, often through problem-focused conversations rather than sales pitches. Each dimension has a range: an architect might primarily allocate budgets as a business steward or actively reshape the company’s products and go-to-market strategy.

Her career examples show why these responsibilities cannot be copied unchanged between employers. At an agricultural biotechnology company, AI could improve hypotheses for gene edits whose validation otherwise required years and substantial land. However, the organization also needed data engineering, integration, IT leadership, and security hiring. Khalaf bought infrastructure rather than recreating it, reserving engineering effort for domain-specific work. In one case, scientists wanted to measure corn embryos as an indicator of later experimental success. Although they requested AI, simple computer-vision blob detection solved the problem without machine learning. At WSO2, by contrast, she describes a mostly technical, curious workforce and a role weighted toward architecture and outward coaching rather than basic internal education.

Her measurement framework deliberately avoids equating activity with value. Token usage is easy to count and easy to game. Instead, she asks whether AI fluency and builders are distributed across functions, whether adoption improves entire workflows rather than isolated tasks, and whether employees have funded access to useful tools. WSO2 combines a small central AI team with AI leads and contributors embedded in product teams. For software products, she tracks agent-consumable documentation and interfaces, build-versus-partner choices, pricing resilience, and dogfooding with an actual feedback loop. Market measures include customer use cases, earned recognition, community participation, and revenue, with early indicators used while new products mature. She stresses that the metric set itself must evolve.

WSO2 provides her example of extending an existing business rather than pursuing AI as a disconnected initiative. She describes adding an AI gateway to API management, agent identity to identity management, and agent-building and lifecycle capabilities around the company’s integration infrastructure. This links experimentation to an architectural direction grounded in existing strengths. She closes by emphasizing that no single organizational design fits every company: the role needs strong CEO relationships and cooperation across functions. Prospective leaders should shape the mandate around what they do well and enjoy, while arranging complementary ownership for responsibilities that are necessary but poorly matched to their strengths.

Suggested actions, from the summary
  • Write an explicit scientist–architect–coach allocation for the role, based on business needs and AI maturity rather than the title alone.
  • Evaluate proposed AI projects against simpler algorithms and existing infrastructure before committing to model development.
  • Combine a central enabling team with capable AI leads inside product teams and other business functions.
  • Replace token-volume targets with a balanced scorecard covering workforce capability, workflow outcomes, product accessibility, customer use, and commercial progress.
  • Secure CEO sponsorship and clear cross-functional responsibilities, then periodically revisit the mandate and its metrics.
Limits of this summary
  • The supplied publisher transcript is untimed; structural validation does not establish semantic completeness.
  • This is an experience-based framework, not a controlled comparison of executive organizational designs.
  • Several charts, research publications, and product visuals are referenced without their full contents or eligible URLs in the transcript.
  • duration_seconds uses the watch and publisher value of 1341; the supplied videos-tab value is 1342 seconds.
  • Company financial figures, adoption statistics, and product capabilities are presented as the speaker’s reports rather than independently verified measurements.

The State of AI in Software Development: Data from 400+ Orgs 

Justin Reock, DX

Data & Evals · Engineering & Infrastructure · Leadership & Culture

Justin Reock presents DX research showing that AI-assisted development is increasing shipping activity without producing uniform improvements in quality, confidence, or business value. His central recommendation is to measure utilization, impact, and cost together, then apply AI to actual delivery bottlenecks rather than assuming faster code generation means dramatically higher productivity.

Key points and full summary
  • Deployment frequency is rising, but Reock stresses that throughput is a proxy rather than a measure of value; perceived delivery speed increased only about 4.5% over a year.
  • Quality outcomes vary substantially between companies. A two-percentage-point increase in change failure rate is significant against the approximately 4% industry benchmark he cites.
  • Perceived maintainability increased almost 4%, while change confidence declined 6%; average PR size grew from roughly 44 to 72 lines and sentiment about incremental delivery fell 10%.
  • Junior engineers use AI more and spend more tokens on comparable use cases, while senior engineers achieve similar reported time savings with less usage.
  • DX's measurement framework combines utilization, impact, and cost, comparing tool-usage cohorts against established productivity and developer-experience metrics.
  • Documentation, modular code, reliable local CI, and non-flaky tests improve both human and agent effectiveness.
  • Examples from Morgan Stanley, Zapier, code review automation, and Spotify illustrate opportunities beyond code generation, including reverse engineering, administrative work, and incident response.

Reock opens by separating shipping activity from useful outcomes. DX observes rising deployment frequency, with regional variation, but that metric says nothing about defects, reversions, or customer value. Engineers' perceived delivery speed increased only about 4.5% over a year. Quality results are volatile across companies: some show change failure increases of two percentage points, large relative to the roughly 4% benchmark he cites. He explicitly cautions against treating these patterns as purely caused by AI; release pipelines and testing already influence outcomes.

The more revealing tension is between easier modification and reduced trust. In research he says covers about 200,000 engineers, perceived maintainability rose almost 4%, while confidence in shipping changes fell 6%. Average PR size increased from around 44 to 72 lines. Reock suggests that slow build pipelines encourage developers to bundle rapidly generated code rather than wait through separate builds. Larger changes increase review burden and potential failure surface, while sentiment about working incrementally declined 10%. Junior engineers use AI most, but senior engineers report similar time savings with fewer tokens, which he links to architectural understanding and better detection of hallucinations.

For measurement, he recommends retaining foundational developer-experience and productivity metrics rather than substituting adoption statistics. His framework tracks utilization, impact, and cost: identify who uses which tools for which tasks, then compare cohorts on outcomes such as PR cycle time, size, review pushback, and quality. Platform readiness matters too. Clear documentation, straightforward data relationships, modular code, reliable CI, and stable tests help agents operate efficiently. DX also gathers qualitative agent feedback about missing context, human steering, and repeated feedback cycles to identify costly workflows.

Reock closes by arguing that code generation addresses only a limited portion of the value stream. One study found median PR-throughput growth of 7.7%, not the promised multiples; meetings, interruptions, and environmental friction can outweigh coding gains. He cites Morgan Stanley's legacy-code interpretation agent, Zapier's reduced stand-up schedule and faster onboarding, automated preliminary reviews, and Spotify's incident-context agent as broader applications. His interpretation is that AI should expand innovative capacity, not merely replace headcount. The practical priority is to locate the binding constraint and improve end-to-end delivery.

Suggested actions, from the summary
  • Track AI adoption alongside deployment frequency, change failure rate, PR size, review friction, and developer confidence rather than reporting usage alone.
  • Compare usage cohorts on established outcome metrics and token costs, accounting for seniority and organizational complexity.
  • Investigate whether slow builds encourage oversized PRs; improve pipeline speed and preserve small, reviewable changes.
  • Prioritize documentation, modularity, local CI reliability, and test stability as agent-readiness investments.
  • Map the delivery value stream and pilot AI on the largest non-coding bottleneck, such as legacy-system discovery, administrative overhead, or incident-context gathering.
Limits of this summary
  • The supplied transcript is untimed and references charts whose underlying data, cohort definitions, and methodology are not included; publisher metadata does not establish semantic completeness.
  • The reported associations do not establish causal AI effects. Reock explicitly acknowledges non-AI influences on quality and delivery.
  • Claims about the METR study and company-specific savings are the speaker's characterizations, not independently verified evidence in the supplied source.
  • References to an upcoming July report and relative study dates do not align transparently with the September 2026 upload date; the recording date is not established.

Stop Renting Your AI's Memory 

Dylan Couzon, Qdrant

AI & Agents · Engineering & Infrastructure · Policy & Safety

Dylan Couzon argues that owning an AI model is insufficient without also owning the persistent memory that makes it personally useful. He demonstrates offline vector memory for a drone and advocates portable local storage with selective, opt-in synchronization rather than provider-controlled personal context.

Key points and full summary
  • Couzon distinguishes inference ownership, which provides autonomy, from memory ownership, which provides continuity across sessions and model changes.
  • He defines memory as writing, retrieving, and forgetting—not simply increasing the context window or accumulating unindexed Markdown files.
  • Retrieval allows explicit filtering and relevance management using topic, recency, and frequency instead of repeatedly placing all history into prompts.
  • The demonstrated embedded vector store runs in-process and offline; Couzon claims quantization can fit a million memories into less than a gigabyte.
  • A drone-video demonstration uses YOLO detections and embeddings to retrieve previously observed objects, including images and first-seen, last-seen, and observation-count metadata.
  • Memory portability depends on maintaining compatible embeddings; sharing across devices or groups should be selective and opt-in because the same mechanism can enable unwanted extraction.

Couzon frames personal AI as an ownership problem rather than merely a model-capability race. Local open-weight models, he argues, are approaching capabilities previously available only through hosted APIs, but a model without personal history remains unfamiliar with its user. Hosted inference can change through retirement, throttling, pricing, or access restrictions. More importantly, provider-controlled memory makes accumulated preferences and corrections dependent on an external service. His distinction is that owning inference provides autonomy, while owning memory provides continuity.

He defines a memory system through three operations: write, retrieve, and forget. A larger prompt or folder of unindexed notes is not equivalent because effective retrieval selects relevant history and supports filters and changing relevance over time. Using a CPU/RAM/disk analogy attributed to Karpathy, he treats the model as computation, the context window as temporary working space, and persistent memory as the durable record. He describes an embedded vector engine with isolated application stores, offline queries, and quantization; the performance and capacity figures are presented as product claims.

The demonstration processes drone footage locally using YOLO object detection, converting observations into embeddings. Couzon reports roughly 92 recognized objects, more than 300 vector representations, and a combined memory-and-engine footprint of about 15 MB. Selecting a coffee-table query retrieves matching observations with images, timestamps, definitions, and sighting counts in under a millisecond, according to the demonstration. He extends this pattern to assistants that retain corrections and preferences. Switching reasoning models or hardware need not discard the store, although he explicitly conditions portability on keeping the same embedding model.

The closing vision extends local memory to smart glasses, families, teams, and robot fleets. Optional cloud synchronization could combine selected observations into shared memory, but Couzon acknowledges that sharing can become extraction without consent. He therefore argues for local storage first and opt-in sharing. His claims about imminent superintelligence and lifelong personal intelligence are predictions and advocacy; the demonstrated mechanism is narrower: persistent, searchable observations stored locally.

Suggested actions, from the summary
  • Prototype a local memory store that persists preferences and corrections across sessions, separately from the reasoning model.
  • Implement explicit write, retrieval, and forgetting behavior, with metadata that supports topic, recency, and frequency filtering.
  • Test retrieval latency and storage footprint on the intended device instead of assuming the demonstration's figures generalize.
  • Plan embedding-model compatibility when moving memory between devices or swapping reasoning models.
  • Keep synchronization disabled by default and require explicit consent for which memories are shared and with whom.
Limits of this summary
  • The supplied transcript is untimed, and publisher metadata marks semantic completeness as unproven; the demo's code, configuration, and visual results are not supplied.
  • Latency, memory footprint, hardware affordability, and model-capability comparisons are speaker claims without reproducible benchmark details here.
  • The alleged government removal of models called Fable and Mythos-5 is not corroborated within the supplied source.
  • Predictions about superintelligence are speculative. The talk does not provide a detailed implementation of forgetting, memory-quality evaluation, or safeguards for sensitive recordings.

MCP Doesn't Suck. Your Agent Does. 

Jan Čurn, Apify

AI & Agents · Engineering & Infrastructure · Data & Evals

Jan Čurn argues that many complaints about MCP arise from inefficient agent harnesses rather than the protocol itself. He demonstrates mcpc, a CLI client that combines MCP's remote connectivity with shell-based discovery and composition, then presents preliminary connector evaluations.

Key points and full summary
  • Eagerly loading every tool definition and routing all results through model context creates token overhead, context degradation, and unnecessary exposure of sensitive values.
  • Sub-agents can isolate context but do not eliminate token costs or the underlying problem of passing large or sensitive data through model context.
  • Progressive discovery loads tool definitions only when needed; code mode lets agents compose calls and process intermediate results outside the conversation.
  • CLIs benefit from familiar shell patterns and progressive discovery by default, while MCP supplies a standardized remote interface and protocol features.
  • mcpc exposes MCP through Bash with JSON output, searchable tool discovery, persistent sessions, OAuth integration, local keychain credential storage, and asynchronous tasks.
  • Preliminary Connector Evals results show mcpc and native CLIs performing similarly in the presented examples, while raw MCP often uses more tokens; Čurn explicitly calls the tests early.

Čurn begins with the contrast between MCP's widespread adoption and growing criticism that it consumes too much context. He agrees that early integrations were wasteful: agents loaded all tool definitions upfront and appended tool results to the conversation, increasing cost and degrading accuracy. His distinction is architectural: MCP specifies tool interaction, not how a harness must manage context. Delegating to sub-agents moves the problem but still incurs token costs and can leave passwords or large datasets inside model-visible context.

He proposes progressive tool discovery and code mode as complementary fixes. Discovery introduces only the definitions relevant to the current task. Code mode treats tools as callable code, allowing agents to search descriptions, compose operations, and process intermediate data without narrating every step through context. CLIs already offer related advantages: agents inspect help as needed and use familiar shell pipelines. Rather than replacing MCP with CLIs, Čurn advocates using MCP for standardized remote access and a CLI as the local interface.

His demonstration introduces mcpc, a lightweight MCP client with no embedded LLM. It connects to a local filesystem server and a remote Apify server, performs browser-based authentication, stores credentials in the operating system keychain, and preserves sessions for reuse across coding agents. Commands can emit JSON for composition with tools such as jq. A grep command searches available tools, while asynchronous task support lets a remote operation continue as the client does other work. He also mentions x402 and sandbox-proxy capabilities without detailing them.

The final section introduces Connector Evals, which compares connectors while holding the agent setup fixed rather than comparing agents alone. In the examples shown, mcpc and native CLIs have broadly similar cost and completion-time results. Raw MCP sometimes finishes faster but consumes more tokens, and performs worse in other examples. Čurn describes the evidence as preliminary. His practical conclusion is to improve discovery, execution, and context handling before attributing poor results to the protocol, and to evaluate MCP-plus-CLI as an alternative to treating the two interfaces as competitors.

Suggested actions, from the summary
  • Audit whether the harness eagerly loads unused tool schemas; replace that behavior with search-based or progressive discovery.
  • Move intermediate data processing into shell scripts or code execution, returning only task-relevant results to model context.
  • Evaluate mcpc for workflows that need MCP remote connectivity with shell composition, persistent authentication, or asynchronous tasks.
  • Benchmark connector alternatives using the same agent and tasks, measuring token cost, completion time, and task success.
  • Check client support for protocol features such as server instructions and asynchronous tasks before concluding that MCP lacks those capabilities.

  • The supplied transcript is untimed, and semantic completeness is not proven; benchmark charts, exact tasks, configurations, and numerical results are not supplied.
  • Connector Evals findings are explicitly preliminary and presented by mcpc's developer, so they do not establish universal superiority.
  • The transcript conflates Unix's 1969 origins with Linux; that historical aside should not be treated as accurate technical history.

Your Coding Agent Is 6 Months Out of Date 

Jakub Hojsan, Exa

AI & Agents · Engineering & Infrastructure · Data & Evals

Jakub Hojsan explains why coding agents need both current external evidence and explicit rules telling them when to retrieve it. He presents Exa’s query-specific highlights, search telemetry, and model-independent interface as infrastructure for grounding code generation and review without filling context windows with entire pages.

Key points and full summary
