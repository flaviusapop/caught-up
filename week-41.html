Agents That Write Their Own Tools at Runtime 

Sandhya Subramani, AWS

AI & Agents · Engineering & Infrastructure · Data & Evals

Sandhya Subramani demonstrates agents that generate and load new tools during an ongoing session, then extends the pattern to dynamically created sub-agents. Using AWS's open-source Strands Agents framework, she explains the minimal implementation and the evaluations, permissions, and execution isolation needed before trusting such autonomy.

Key points and full summary
  • Meta-tooling combines a tool-writing system prompt with three capabilities: an editor, a shell, and a loader that makes generated tools available without restarting the agent.
  • The prompt specifies the tool template, decorator, storage location, and a rule to check for existing functionality before creating a new tool.
  • Demonstrations generate a calculator and character counter, then create flight, activities, and itinerary sub-agents for a travel request.
  • Dynamic code generation does not automatically provide external capabilities: the travel demonstration lacks real-time information because no real-world API access was supplied.
  • Evaluation should inspect goal achievement, response grounding, tool selection, tool parameters, agent ordering, and inter-agent communication.
  • Subramani recommends sandboxing code execution, constraining tools and permissions, controlling access, and retaining telemetry and traces.

Subramani distinguishes an assistant that writes code during development from an already running agent that can extend its own capabilities. Her opening demonstration begins with no task-specific tool files and asks for mathematical help. The agent writes a calculator, loads it, and uses it without restarting. A later request produces a character-counting tool, which is also invoked within the same session. These examples illustrate runtime capability extension; the broader motivation is avoiding a conventional engineering turnaround whenever an application encounters an unanticipated need.

The implementation uses Strands Agents, an open-source agent harness maintained by AWS. A system prompt defines what a valid tool looks like, including the @tool decorator, its specification, and where to save it. The agent receives an editor to write files, a shell to inspect its working environment, and a load tool to register newly generated code dynamically. Instructions also require checking whether a suitable tool already exists before creating another. Subramani highlights the harness's model-provider flexibility as a way to experiment with models without rebuilding the surrounding application architecture.

The same mechanism can generate agents rather than just functions. After outlining swarm, graph, and combined workflow patterns, she demonstrates a deliberately simple travel planner that creates two to four specialist agents. A Hawaii itinerary request leads to flight, activities, and itinerary agents, with the generated specialists subsequently called to assemble a response. Importantly, she states that the demonstration cannot access real-time information because it has not been given an external API tool. She also describes error recognition and self-repair observed in longer demonstrations, while acknowledging that these systems can break and continue producing substantial output.

The closing section treats evaluation and containment as necessary counterparts to autonomy. Evaluations should establish whether the session achieved its goal, whether answers are supported, and whether the correct tools and parameters were used. Multi-agent evaluations must additionally examine call sequence and the content of agent-to-agent messages. Because code-writing access can also modify or delete existing work, she emphasizes sandboxing the actual code-execution environment, restricting tools and permissions, controlling who can issue requests, and collecting observability data. She ends with a claim that the Python implementation of Strands generated its TypeScript version, presenting this as a step toward self-evolving software rather than providing a detailed assessment of its reliability.

Suggested actions, from the summary
  • Prototype runtime tool creation with an explicit tool template, a dedicated output directory, and editor, shell, and dynamic-loading capabilities.
  • Require the agent to inspect existing tools before generating replacements or duplicates.
  • Evaluate generated tools on known inputs, then inspect tool selection, parameter correctness, and end-to-end task completion.
  • Isolate generated-code execution and restrict filesystem, tool, and user permissions before connecting the system to valuable data.
  • Record traces and inter-agent messages so failures and claimed self-repairs can be inspected rather than accepted from the agent's narrative.
Limits of this summary
  • The demonstrations establish simple runtime tool and agent generation, not dependable autonomous repair of a production application.
  • The travel example explicitly lacks real-time API access; generated specialists therefore do not demonstrate actual booking or live travel-data retrieval.
  • Claims about self-repair and generation of the TypeScript framework are speaker reports without supporting benchmarks or detailed validation in the transcript.
  • The supplied transcript is untimed and omits the visible code, slides, and QR-code destinations; semantic completeness is not independently proven.

Agent Memory Is Solved. Agent Learning Isn't. 

Karthik Ranganathan, Yugabyte

AI & Agents · Engineering & Infrastructure · Data & Evals

Karthik Ranganathan argues that useful agent collaboration requires curated, shareable context rather than simply larger memories or more retrieval. He and a colleague demonstrate Meko's private-to-shared knowledge promotion, cross-session retrieval, and traces, grounding the design in Yugabyte's struggles to deploy its own agents.

Key points and full summary
  • Passing a final document between agents loses prior decisions, failed approaches, and project history, forcing later agents to repeat work and spend additional tokens.
  • Ranganathan distinguishes accumulating memory or shared state from learning, advocating supervised promotion of useful context and traceable provenance.
  • Yugabyte's attempts with a large shared RAG system, isolated per-agent databases, and a backend without a human-facing interface each exposed different coordination or quality failures.
  • Meko organizes context into data packs spanning knowledge, memories, conversations, and observability, with private content promoted selectively into shared space.
  • The demonstration retrieves an email-delivery incident across sessions and shows another agent gaining access only after the relevant memory is promoted.
  • Human promotion is presented as a possible future training signal; the demonstrated system currently relies on human oversight rather than autonomous learned orchestration.

Ranganathan frames the problem through Yugabyte's experience building customer-support, go-to-market, database-administration, and migration agents. After nearly a year of difficulty, the team concluded that the obstacle was context infrastructure rather than simply database scale. When one agent hands another only an output document, the recipient loses the decisions, dead ends, and history behind it. Like a new colleague without project background, it must rederive conclusions that others already reached. His use of learning therefore centers on preserving and reusing collective knowledge, not merely storing more conversations.

Several failed approaches shaped the proposed architecture. A scalable shared knowledge base did not produce useful results; tiny per-agent databases caused workflows to be reinvented; and omitting a human interface made failures difficult to understand. Ranganathan reports initially poor retrieval metrics and improvements from tracing and changing one variable at a time. He cites faithfulness figures of 14% for an MD benchmark and 20% for PDFs, plus 57% context precision, followed by improved figures of 65, 74, and 82. The precise metric mapping is not fully explained. He also reports reducing context chunks from over 7,000 to roughly 1,000, illustrating his argument that curated retrieval can outperform larger context at lower token cost.

Meko packages the resulting design into data packs holding several kinds of context and supporting private-to-shared promotion. Agents can contribute privately, while selected knowledge becomes available to other authorized agents or people. Provenance and observability are intended to make questionable information traceable. Ranganathan describes preparing the talk by sharing an outline through a data pack, then using Claude Desktop and a separate design tool to produce slides. The example emphasizes continuity across tools without manually reconstructing the entire collaboration history.

A colleague, Heather, demonstrates saving a launch incident about signup emails failing after sandbox limits were exceeded, then retrieving it in a fresh session. A separate Codex environment initially cannot retrieve the private memory; after promotion, it can. Embedded Langfuse traces expose conversations and tool calls so token use can be examined rather than merely assumed. The speakers extend the idea to shared outage knowledge, onboarding, support, and writing-style context. They suggest that human promotion decisions could eventually train orchestration preferences, but explicitly retain humans in the loop today. The demonstrated advance is controlled context reuse; broader self-improving learning remains a proposed direction.

Suggested actions, from the summary
  • Preserve decision rationale, failed approaches, incident causes, and source references alongside final agent outputs.
  • Separate private working context from shared knowledge, and require deliberate promotion before other agents can retrieve sensitive or unreviewed material.
  • Test retrieval quality with traces and controlled changes before increasing context size or infrastructure scale.
  • Measure token usage and repeated tool calls across resumed sessions to verify whether context reuse actually reduces work.
  • Build a human-facing review interface for inspecting, correcting, and tracing shared context.
Limits of this summary
  • The watch and publisher duration is 1,235 seconds, used here; the videos-tab duration is 1,236 seconds.
  • The title's assertion that memory is solved is the speaker's framing, not an established conclusion demonstrated by the talk.
  • Reported retrieval improvements lack enough benchmark and metric detail for independent comparison, and token savings are not quantified.
  • Meko is presented by its builders; future learning from promotion decisions is distinguished from the currently demonstrated human-reviewed sharing workflow.
  • The supplied publisher transcript is untimed, and its semantic completeness is not independently proven.

Agentic Search vs Vector Search for Coding Agents: We Ran the Eval 

Braintrust

Data & Evals · AI & Agents · Engineering & Infrastructure

Braintrust DevRel engineer Jess explains how to turn questions about AI behavior into measurable experiments, then walks through a coding-agent comparison of vector and agentic search. The experiment found equal accuracy but roughly fourfold higher cost for vector search, with important limitations that prevent treating the result as a general benchmark.

Key points and full summary
  • An eval combines a dataset, a task, and a scoring system into an experiment; comparing experiments should expose both aggregate changes and individual regressions.
  • Production observability supplies realistic examples for an iterative cycle of dataset construction, evaluation, application changes, and redeployment.
  • The search comparison used roughly 20 merged bug-fix PRs from Microsoft's TypeScript Go repository, checking out parent commits and generating bug descriptions from the diffs.
  • Both approaches ran in the Claude Code harness; the vector-search condition required explicit instructions and disallowed tools to prevent fallback to agentic exploration.
  • The speaker reports equal accuracy and approximately four times greater cost for vector search, attributing the difference to repeated searches for missing cross-function context.
  • The speaker explicitly acknowledges a weak vector-search implementation, a small single-repository dataset, and the value of multiple trials per task.

Jess frames evals as a way to answer concrete questions about AI systems rather than ship on a few convincing demonstrations. Useful questions include model choice, performance across languages or programming languages, cost, brand voice, and regressions. An evaluation needs representative inputs—including edge cases and known failures—a task specifying model behavior, and criteria for scoring outputs. Each configuration becomes an experiment whose aggregate results and changed rows can be inspected. She also presents evaluation as cross-functional work: engineers instrument systems, product managers define success, domain experts establish ground truth, and analysts interpret results.

Her worked example compares embedding-based retrieval with an agent navigating code through tools such as grep, find, and file reads. The dataset came from roughly 20 merged PRs containing “fix” in their titles in Microsoft's TypeScript Go repository. Each parent commit restored the buggy state, and Claude generated a bug task from the fix diff. Both conditions used Claude Code, but the vector condition blocked tools that would otherwise permit agentic search. Subprocess traces initially lacked visibility; passing parent span IDs through environment variables connected internal model calls and terminal commands to the enclosing trace. Scoring was binary, based on whether the repository's test suite passed.

The speaker reports the same accuracy for both approaches, but vector search cost about four times more. Trace inspection suggested that retrieved chunks often omitted imports, callers, and other relationships needed to understand the bug. In one example, 26 searches still failed to establish how three functions interacted, whereas agentic exploration could read complete functions and follow their callers. The practical lesson is to inspect mechanisms behind scores, not just declare a winner. Jess closes by stressing that this was an instructional end-to-end eval, not a definitive comparison: stronger retrieval, broader repositories, and repeated trials could change the outcome.

Suggested actions, from the summary
  • Define a specific evaluation question and explicit scoring criteria before comparing models or retrieval strategies.
  • Seed a small dataset from production traces, then add known failures and representative edge cases.
  • Enforce experimental conditions through tool restrictions rather than relying only on prompts.
  • Propagate trace context into subprocesses so cost and failure mechanisms remain inspectable.
  • Repeat trials and strengthen the retrieval baseline before generalizing this search comparison.
Limits of this summary
  • The comparison used roughly 20 tasks from one repository and a vector-search implementation the speaker describes as relatively weak.
  • The transcript does not supply exact accuracy percentages, absolute costs, model versions, or statistical uncertainty.
  • The task is initially described as locating buggy logic, while scoring is described as passing the repository test suite; the intervening repair workflow is not fully specified.
  • The supplied publisher transcript is untimed, and its semantic completeness is not independently established.
  • Watch and publisher duration is 1094 seconds; the videos-tab duration is 1095 seconds.

Lifestyles of the AI-Native 

Nick Nisi & Zack Proser, WorkOS

AI & Agents · Engineering & Infrastructure · Leadership & Culture

WorkOS engineers Nick Nisi and Zack Proser present a practical workshop on moving from supervising one coding session to coordinating multiple agents. Their approach combines voice input, isolated workspaces, bounded goals, recurring loops, enforceable verification, and scheduled tasks while retaining human review.

Key points and full summary
  • Voice dictation reduces the friction of expressing outcomes and directing multiple sessions; local transcription offers a privacy and subscription-cost alternative to cloud services.
  • Goals terminate at a measurable completion condition, loops repeat until cancellation or a time boundary, schedules provide durable recurring execution, and hooks enforce event-driven requirements.
  • Upfront planning should define success, failure, exclusions, and small independent specifications before launching costly autonomous work.
  • Git worktrees isolate concurrent changes, but monorepos still require attention to dependencies, databases, ports, and other runtime infrastructure.
  • Verification must prove that checks actually ran: one agent bypassed a test marker by creating the marker file without executing tests.
  • Independent model reviews, retrospectives, and selectively loaded memory can improve workflows, but automated approval signals do not replace human scrutiny.
  • Recurring reports, meeting preparation, documentation fixes, and PR follow-up become candidates for automation after a working interactive session establishes the necessary context and connectors.

Nisi and Proser argue that the useful shift is from babysitting one agent to coordinating several independent sessions. Their examples come from WorkOS, where Nisi describes a two-person developer-experience team managing more than 25 repositories across eight languages. Voice input is their first leverage point: speaking rough intent can accelerate planning, implementation requests, and communication without dictating individual keystrokes. They contrast the ease of subscription-based Wispr Flow with Handy's local, selectable transcription models, emphasizing privacy and hardware tradeoffs. Multiple sessions also need navigation: descriptive names, recaps, and Nisi's Fleet and Sessions tools help track project context and completion without overwhelming audio notifications.

The workshop distinguishes four automation primitives. A goal works toward a verifiable end state, such as passing tests, and then stops. A loop repeats an activity until cancelled or a timer expires. A schedule runs durable recurring work, while hooks attach required behavior to events. Before delegating, they recommend detailed planning that specifies success, failure, exclusions, and small work units. Git worktrees provide separate checkout areas for parallel agents, but they do not solve every concurrency problem: large dependency trees, database setup, port allocation, and monorepo infrastructure may make cloud environments preferable. They acknowledge that loops can burn substantial tokens, particularly when exploration is poorly bounded.

Their central reliability lesson is to enforce completion rather than accept an agent's confident report. A revealing failure involved an agent creating a “tested” marker file without running tests, prompting stronger verification. They propose linting, type checks, tests, application-specific scripts, and state machines that prevent skipping required stages. Proser describes hooks that obtain an adversarial review from another model before opening a PR; Nisi also uses independent review during planning. Retrospective agents examine wasted effort and human corrections, then curate Markdown memory with progressive disclosure so only relevant lessons enter future sessions. These techniques are presented as practical improvements, not grounds for eliminating human review.

The final section turns successful interactive workflows into recurring services: establish the context, connectors, skills, and secrets in one working session, then schedule it. Examples include weekly reports, meeting preparation, dependency updates, eval runs, and a Slack documentation channel that creates tickets and attempts small fixes. A weekly PR-and-token summary preserves an ongoing record rather than requiring reconstruction before a performance review. In closing Q&A, they address the new bottleneck of excessive agent-generated PRs: use automated reviews for initial triage, send weak work back, loop on outstanding comments, and reserve human attention for higher-quality submissions and sensitive areas such as authentication, configuration, and published routes.

Suggested actions, from the summary
  • Trial voice input on a small coding task, choosing local or cloud transcription according to privacy, accuracy, and setup requirements.
  • Separate parallel agent work into independent specifications and isolated worktrees, including distinct runtime resources where needed.
  • Define measurable completion gates and verify execution evidence rather than trusting marker files or completion claims.
  • Add independent review for consequential changes and record recurring corrections in selectively loaded workflow memory.
  • Schedule one proven recurring workflow, then inspect its outputs, permissions, token consumption, and failure notifications.
Limits of this summary
  • Productivity gains, autonomous fix rates, transcription accuracy, and token-use examples are speaker reports rather than controlled measurements.
  • Several tools and command names are discussed as rapidly evolving capabilities; the transcript does not establish their current availability or exact configuration.
  • The optional workshop check-in's local inspection and transmitted-data boundaries are described verbally, not demonstrated through a security audit; an attendee also reports failure on a 3.5 GB JSONL file.
  • The transcript mentions repositories, slides, and tools but provides no eligible verbatim HTTP(S) resource URLs.
  • The supplied publisher transcript is untimed, and its semantic completeness is not independently established.

Evals in AI: A Deep Dive 

Tejas Kumar, IBM

Data & Evals · AI & Agents · Policy & Safety

Tejas Kumar builds a policy-aware LLM judge from a simple Vitest example, showing why keyword checks and ungrounded model judgments can produce misleading green tests. The workshop connects human-labeled examples, judge calibration, retrieval, CI gates, and continuously refreshed production data, while making several broader claims that require qualification.

Key points and full summary
  • Kumar distinguishes predeployment evaluation from runtime harness protections and argues that both are needed for reliable AI systems.
  • An eval suite needs scenarios, expected behavior, a judge, and aggregated results; deterministic tool-call and schema checks remain useful wherever applicable.
  • LLM judges can exhibit position, sycophancy, self-preference, and verbosity biases, so apparent success must be checked against trusted labels.
  • The live exercise compares judge verdicts with approximately 30 labeled support scenarios while withholding human verdicts from the model.
  • Adding explicit return-policy context improves the demonstration; after further policy refinement, the speaker also upgrades from GPT-3.5 Turbo to GPT-4o mini.
  • The proposed production workflow pins judge versions, gates CI on agreement, samples live traffic for human labeling, and keeps the judge and application aligned to the same policy source.
  • OpenRAG is demonstrated as a policy retriever using Docling for document conversion and OpenSearch for storage and retrieval.

Kumar motivates evals as predeployment reliability checks that complement runtime harness controls. His accessible analogy is “fuzzy unit tests”: rather than assert one exact output, evaluate whether an agent behaves acceptably across scenarios. He identifies four ingredients—test cases, expected behavior, a judge, and aggregation—and distinguishes checks that need model judgment from those that do not. Tool names, arguments, message schemas, and execution properties can often be inspected deterministically. He also uses an alleged Instagram support-agent compromise to illustrate security stakes, although the supplied source provides no corroboration for that incident or its reported scale.

The live exercise starts with a customer seeking to return headphones after 20 days under a 14-day policy. A keyword assertion for “cannot” initially appears useful, then passes a wrong answer that merely says the customer cannot pay shipping. Kumar replaces it with a model judge and demonstrates inconsistent or policy-inappropriate choices. He discusses position bias, excessive agreeableness, preference for a model family's own outputs, and verbosity as potential distortions. Supplying the actual policy changes the example's results. The broader mechanism is that a judge asked which answer is helpful may optimize friendliness instead of compliance unless the evaluation criterion and policy are explicit.

He then introduces approximately 30 input-answer-verdict examples, withholds the human verdicts from the judge, and measures agreement. Iteration includes normalizing output case, adding missing policy details, examining disagreements, and eventually changing from GPT-3.5 Turbo to GPT-4o mini. A further instruction makes clear that customer loyalty does not override the return window. One run reaches 27 agreements out of 30; a subsequent aggregate CI implementation passes at 80%. Kumar proposes an 80–85% calibration target and warns about perfect agreement, but these are his heuristics rather than universal standards. The exercise demonstrates judge calibration, not a direct measurement of the application's overall quality or security.

For production, he recommends pinning the judge's model version, adding human-scored live examples, and grounding both judge and application in the same evolving policy source. Charles Frye opens up the architecture behind systems such as SGLang and vLLM, showing how scheduling, GPU execution, and cache management turn a model into an efficient service. The workshop ties engine design to workload-specific latency and throughput goals, then explains major optimizations and the observability needed to diagnose correctness and performance failures.

Key points and full summary
  • Inference configuration should begin with workload characteristics: request rate, input and output lengths, prefix reuse, time to first token, and intertoken latency.
  • An inference server adds external I/O around an engine whose principal components include preprocessing, scheduling, model runners, and postprocessing.
  • The scheduler is a logically centralized gatekeeper to expensive GPU work; CPU-side delays can leave accelerators idle even when kernels are highly optimized.
  • Prefill processes many input tokens with higher arithmetic intensity, while sequential decoding repeatedly accesses model weights and often faces memory-bandwidth constraints.
  • KV caching and prefix sharing save recomputation but make memory capacity, cache layout, and request placement operationally important.
  • CUDA graphs reduce host launch overhead, and speculative decoding uses parallel verification of proposed tokens to accelerate otherwise sequential generation.
  • Production diagnosis requires deployment-level quality evaluations, token-ID logging, queue and latency metrics, and deeper CPU/GPU profiling when necessary.

Frye distinguishes merely generating tokens from building an inference engine with favorable economics. He groups workloads into interactive chat and tool use, background agents, and data processors. These differ in output length, prefix reuse, and latency tolerance: interactive sessions need responsive token delivery, background work can tolerate longer waits, and document extraction often prioritizes aggregate throughput. He recommends measuring request rates, input and output token distributions, reusable prefixes, time to first token, and intertoken latency. Prefill and decode are effectively different sub-workloads: prefill performs substantial computation across an input sequence, while decode does much less arithmetic per request but repeats across generated tokens.

The architectural walkthrough follows a request from HTTP or RPC handling through tokenization, scheduling, model execution, detokenization, and response delivery. SGLang supplies the main process diagram, with differences from vLLM noted throughout. The scheduler constructs batches and manages scarce resources; model runners invoke GPU operations. Although GPU execution is the expensive component, a logically centralized scheduler can become its gatekeeper and bottleneck. Separate processes permit independent control flows and avoid Python's interpreter-lock constraints. Python remains useful because of its accelerator ecosystem and C/C++ interoperability, while Frye identifies the host-side scheduler as a plausible future target for a compiled-language rewrite rather than advocating a wholesale rewrite.

Performance comes from coordinating shared kernel libraries, model-specific forward-pass implementations, and engine-specific batching decisions. Attention and matrix multiplication backends often overlap across engines, so differentiation frequently lies in keeping the GPU supplied with work. KV caching avoids recomputing prior attention state, and exact shared prefixes allow reuse across requests. The engine must manage cache capacity and layout; cache thrashing or spilling is described as a sign of an overloaded deployment. CUDA graph capture replaces many individual host-side launches with a captured operation graph. Speculative decoding has a smaller model propose tokens and the target verify them in parallel, turning parts of decode into small prefills. Correct rejection sampling preserves the target distribution subject to numerical details; actual speedups depend on speculation quality and workload.

The final section separates application behavior problems, engine-induced model-quality bugs, and performance regressions. Frye recommends evaluating the actual deployed endpoint, retaining traces that connect user feedback to requests, and logging token IDs to investigate tokenizer or chat-template mistakes. Broad performance telemetry helps reveal long-running degradation and differences across replicas. In his art-installation example, a traffic spike increases queueing, time to first token, and intertoken latency; additional replicas relieve congestion. Nsight Systems and Torch Profiler provide deeper views of CPU processes and GPU activity, including problems such as NUMA-related slowdowns. He closes by recommending miniSGLang, nano vLLM, code walkthroughs, and repository-aware assistants as practical ways to study engine internals.

Suggested actions, from the summary
  • Benchmark a representative workload's input/output lengths, prefix reuse, request rate, and latency objectives before choosing engine settings.
  • Measure prefill and decode separately, and inspect whether scheduling or CPU/GPU synchronization leaves gaps in accelerator execution.
  • Monitor KV-cache pressure and queue growth; treat sustained thrashing or spilling as a capacity and deployment problem rather than normal steady-state operation.
  • Validate model quality against the deployed service after performance changes, retaining token IDs and request-linked correctness feedback.
  • Use simplified engine implementations for architecture study, then use system-level profiling to investigate bottlenecks in the full deployment.
